# Architecture

This document describes the stable boundaries of the smolikja.team frontend.
It is organized by subsystem rather than as a catalog of every React component.

## Route families

| Public route | Implementation | Responsibility |
| --- | --- | --- |
| `/{locale}` | `src/app/[locale]/page.tsx` | The localized landing page, its metadata and Open Graph image. Supported content URLs are always prefixed: `/cs` and `/en`. |
| `/cs/bezpecnost-aplikaci`, `/en/app-security` | `src/app/[locale]/bezpecnost-aplikaci/`, `src/app/[locale]/app-security/` → `src/app/[locale]/_security/security-route.tsx` | The app-security page with its own share image. The slug differs per locale (`securityPath` in `src/config/pages.ts`), so each locale has a route folder that 404s for the other locale and delegates to the shared implementation. |
| `/{locale}/privacy` | `src/app/[locale]/privacy/page.tsx` | What the site collects and why; linked from the contact form and footer. |
| `/` and any unprefixed path | `src/proxy.ts` | 307 redirect to the visitor's locale (cookie → `Accept-Language` → default). |
| unmatched `/{locale}/…` | `src/app/global-not-found.tsx` | Fully server-rendered, localized 404 with its own `<html lang>`. |
| `/robots.txt`, `/sitemap.xml`, `/manifest.webmanifest`, `/icon.png`, `/apple-icon.png` | Metadata files in `src/app/` | Search-engine and install metadata generated by Next.js file conventions. |
| `/assets/*`, `/brand/*` | `public/` | Videos, app screens, owner photos, logo, PWA icons. Static; never redirected. |

`src/proxy.ts` applies locale redirects only to localizable page routes. The
metadata files, the Open Graph image route, framework internals, API paths and
anything with a file extension are excluded by its matcher. Keep `proxy.ts`
beside `src/app/`; this is the Next.js 16 file convention used by this project.

## Server and client boundaries

Server Components are the default. They load the dictionary, build metadata
and compose the page without shipping message catalogs or environment
variables to the browser.

Use a Client Component only when the subtree needs browser state, effects or
event handling. Current client islands:

| Island | Why it is client-side |
| --- | --- |
| `landing/mobile-menu.tsx` | Open/close state of the small-screen menu (shadcn `Sheet` on Base UI). |
| `landing/scroll-gallery.tsx` | Work screens on a strip driven by the page's vertical scroll (`motion` `useScroll`): the stage pins below the header and its added height becomes horizontal travel, with a progress bar. No wheel or touch events are intercepted; with reduced motion it is a plain horizontally scrollable strip (CSS-only switch, so server and client markup match). |
| `landing/hero-device-stack.tsx` | The two hero devices; pointing at (or tapping) the back one shuffles it to the front with a `motion` keyframe animation. |
| `landing/contact-form.tsx` | `useActionState` around the contact Server Action; remounts fields with restored values after a failed attempt. |
| `landing/faq-section.tsx` → `ui/accordion.tsx` | Expand/collapse of the FAQ (Base UI accordion). |
| `landing/reveal.tsx` | The one restrained entrance — the hero devices — via `motion`; with reduced motion only the fade remains. |

Everything else, including the sticky header and its animated wordmark
(`landing/site-logo.tsx`, a plain `<video>` blended onto the header), is a
Server Component. Values
crossing from a Server Component to a Client Component are serializable plain
data; Server Actions are the supported function exception.

Language switching is plain links (`layout/language-switcher.tsx`) — visiting
`/en` makes the proxy remember the choice in the `NEXT_LOCALE` cookie, so it
works without JavaScript.

Server-only integration code is marked explicitly:

- `src/app/actions/contact.ts` owns the contact mutation.
- `src/lib/contact-mail.ts` owns delivery through Resend.

Do not add an internal Route Handler merely to call it from a Server
Component. Read data directly in the Server Component layer and use Server
Actions for mutations initiated by this UI.

## Source ownership

| Location | Owns |
| --- | --- |
| `src/app/` | URL structure, layouts, page composition, metadata, the global 404 and Server Actions. |
| `src/components/landing/` | Landing-page sections and their composition (`landing-page.tsx`), plus the small feature wrappers (`cta-link.tsx`, `phone-screen.tsx`, `section-heading.tsx`) that apply the page's sizes to generated primitives. |
| `src/components/layout/` | Shared layout helpers (language switcher). |
| `src/components/icons/` | Inline brand and third-party marks. |
| `src/components/ui/` | Generated shadcn primitives (Base UI + `cva`). Regenerate with the CLI; do not hand-edit their API. |
| `src/config/` | Locale-independent structural data: site URLs and links, navigation and the primary action target, work screens and kinds of projects, page paths, legal identity, paths and dates, brand assets. |
| `src/i18n/` | Locale types, language negotiation, dictionary loading and template formatting. |
| `src/lib/` | Shared server/domain utilities: fonts, `cn()`, metadata helpers, rate limiting, mail delivery, OG rendering. |
| `messages/` | Localized user-facing copy. |
| `public/` | Static assets served from the site root. |
| `scripts/` | Repository tooling (`check-docs.mjs`). |

Prefer the narrowest existing subsystem. Create a new directory only when a
feature has a distinct responsibility and more than one collaborating module.

## Data flows

### Localized page

The locale segment is validated against `src/i18n/config.ts`. The page loads
the matching typed catalog, and `landing-page.tsx` passes only the dictionary
subtree each section renders, in reading order: offer (hero, with the owner's
name and photo) → four services (work it out, build, secure, grow) → my work
(scroll-driven screen gallery) → experience (kinds of projects) → security
teaser → how a collaboration runs → about (bio and portrait) → working with
AI agents → assurances → FAQ → enquiry, one topic per screen. Structural values
(screen ids and sizes, experience ids and technology tags, anchors, page
paths) come from `src/config/`, never from translation files;
`src/i18n/dictionaries.ts` cross-checks at load time that every configured
screen and experience has copy.

Navigation is resolved per page by `navLinks()` in `src/lib/navigation.ts`:
anchors stay bare on the landing page and point back to it from other pages,
and the security item links to the localized security page. The header hides
the primary action below the `sm` breakpoint (the menu, hero and contact
section repeat it) so it never overflows a 320 px screen.

### Work section

`src/config/work.ts` lists the gallery screens (neutral ids, intrinsic sizes),
the kinds of projects with their technology tags, and the two hero screens.
The section deliberately names no client and no product: captions and cards
describe the industry and the work. Adding a screen or a kind of project is a
config entry plus copy — see [Localization](localization.md).

### Contact form

The client form invokes a Server Action. The action applies the honeypot,
process-local IP rate limiting and Zod validation, then hands the message to
the Resend delivery module. Failed submissions return the entered values and
the invalid fields; the browser never sees the API key. Details and
limitations in [Contact form](contact-form.md).

## Styling

Tailwind v4 with the shadcn `base-nova` preset. Semantic tokens are defined
once in `src/app/globals.css` as a single light theme (the palette from the
redesign plan, converted to oklch); there is no dark variant. Components use
semantic utilities (`bg-card`, `text-muted-foreground`, `bg-primary`) — never
raw colours — and the real application screens supply most of the colour.
Primary controls are 48 px tall and form text is 16 px; the generated
primitives are not edited for this, the landing wrappers add the sizes.

Every section (`landing/section.tsx`) is at least one screen tall minus the
sticky header (`100lvh`, so it still fills the screen when a mobile browser
hides its toolbar) and centres its content; longer sections simply grow.
Sections are told apart by alternating plain and tinted backgrounds, not by
rules; `FaqSection` and `ContactSection` take a `tone` because their place in
the alternation differs between the landing and security pages. The
header is solid, not translucent: the wordmark video (white logo on black) is
inverted and multiplied onto it, and only an opaque surface lets the black
frame disappear without a visible rectangle.

## Sources of truth

- User-facing copy: `messages/<locale>.json`, typed by `src/i18n/dictionary.ts`.
- Supported locales and URL behaviour: `src/i18n/config.ts` and `src/proxy.ts`.
- Site URL, owner name, e-mail, external links, navigation: `src/config/site.ts`.
- Owner photos and brand assets: `src/config/assets.ts`.
- Work screens, kinds of projects and the hero composition: `src/config/work.ts`.
- Security page paths, the quoted statistic's source and the service order: `src/config/pages.ts`.
- Operator identity (name, IČO, registered address), privacy page path,
  effective date and authority link: `src/config/legal.ts`. The footer and the
  privacy page render the identity through the `operator` catalog templates.
- Dependency versions and commands: `package.json`.
- Deployment commands: `nixpacks.toml` and `next.config.ts`.

Documentation should explain why these values matter and how systems
interact; it should link to the source rather than copying change-prone
values.
